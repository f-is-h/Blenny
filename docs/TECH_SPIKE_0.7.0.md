### Command-drag protocol and persistence layers

The owner's storage premise is correct, but macOS 27 does not expose one public
"move this item beside that item" call. Read-only AppKit runtime inventory shows
the following private path on build `26A5416b`:

1. MenuBarAgent hosts each composited item through `NSStatusItemHost` and an
   `NSStatusItemHostingView`. The host carries a bundle identifier, persistent
   identifier, preferred position, drag permission, scene and insertion/priority
   inputs.
2. The hosting view receives `mouseDragged:`. AppKit's private status-item scene
   types include `_beginCreationDragWithHitPoint:`, `_dragStatusItemWithOffset:`,
   `_itemMovedDuringDrag` and `_completeStatusItemDrag`.
3. A locally constructed, never-sent `NSStatusItemStartDragAction` encodes only
   the drag offset (`ox`, `oy`) in its BoardServices action dictionary. This is
   transport-shape evidence, not authorization to forge or send a remote drag.
4. `NSStatusItemSceneHostSettings` exposes the host's `preferredPosition`, while
   `NSStatusItemSceneClientSettings` exposes the owning application's
   `savedPreferredPosition`, `autosaveName` and `allowItemDragging`. The scene is
   therefore a two-way host/client protocol; a private backing setter on a local
   runtime object is not a supported cross-process reorder API.

Position persistence has at least two distinct layers:

- AppKit stores an owning item's saved value under
  `NSStatusItem Preferred Position <autosaveName>` in that application's standard
  defaults. For a sandboxed application this can be its container preference
  file; an ordinary preference file with the same domain may coexist and differ.
  Apple's public `autosaveName` property documents only the unique name used to
  save and restore status-item configuration. It does not expose the numeric
  position contract. Hammerspoon's public implementation independently reads,
  caches and restores this exact owner-default key around item removal.
- MenuBarAgent also reads the private global override dictionary
  `TrailingItemPreferredPositions` from `com.apple.MenuBarAgent`. The successful
  self-only run proves that a correctly formed `status:<bundle>::<autosave>` key
  in this table can physically move a third-party status item on this runtime.
  The table can be absent while the owner-default values still describe a full
  existing layout, so absence is not an empty-order snapshot.
- Apple Control Center and legacy system items additionally retain owner-specific
  positions in their own preferences. Those Apple values remain read-only and
  cannot be treated as Blenny's global baseline or recovery source.

This also explains why the earlier Usage4Claude experiment was inconclusive. It
wrote the ordinary preference domain, while the sandbox-container copy held a
different value; it did not establish which value the live scene supplied to
MenuBarAgent. An incorrect owner store, an incorrect internal identity, or a
missing agent layout invalidation can each produce a successful preference
readback without a physical move.

A read-only comparison of current AX frames with exact owner-default values also
rejects a simple calibration shortcut. Nearby third-party items do not form a
monotonic position/value sequence, and some sandboxed owners have conflicting
ordinary/container values. The successful Blenny weight `700` therefore cannot be
extrapolated safely to a guessed value such as “larger than the current maximum”
to reach the arrow. That would be another blind write without a deterministic
target or exact physical inverse.

Thaw's public macOS 27 orchestration uses the agent-table path rather than a
public AppKit reorder method. Its tests show generic third-party keys, insertion
of an unweighted item, permutation of existing numeric slots for batch order,
one global-dictionary write and one own-item layout nudge. The item manager then
checks AX geometry, performs bounded private-path retries, and can fall back to
synthetic Command-drag; its normal cache/reconciliation machinery can try again
later. The key-resolution and midpoint implementation is delegated to the
unavailable `PlatformRuntimeKit` binary package, so the public repository does
not supply a complete identity or weight contract. Blenny cannot copy, link or
infer that missing contract, and its nudge, synthetic-input, polling and automatic
reconciliation paths violate this spike's safety boundary.

Bartender independently claims cursor-free macOS 27 moves. Read-only static
strings in its preview refer to the same global table, live-item resolution,
position write plans, original-position backups, preference import/synchrony,
nudge and restore operations. That closed-source evidence is consistent with the
same architecture, but does not prove an exact safe algorithm. Bartender's own
release notes report live-layout drift, multi-item limitations and menu-bar
unresponsiveness after repeated moves, which are material product risks rather
than edge cases Blenny may hide with automatic repair.

### Current menu-bar manager implementation survey

A fresh 2026-09-01 comparison used current upstream source snapshots under
ignored LocalData. It changes one earlier characterization: the cursor-free
position-table implementation is real, but it is not the general stable path used
by current open-source managers.

- [Hidden Bar](https://github.com/dwarvesf/hidden/blob/develop/docs/ARCHITECTURE.md)
  and [Ice](https://github.com/jordanbaird/Ice/blob/main/Ice/MenuBar/ControlItem/ControlItem.swift)
  create their own divider status items. Expanding a divider to a very large
  width pushes items on one side off-screen; users initially place items across
  the divider with native Command-drag. This is section concealment, not an API
  for setting another owner's order.
- Ice's item mover and
  [SaneBar's documented mover](https://github.com/sane-apps/SaneBar/blob/main/ARCHITECTURE.md#icon-moving-pipeline)
  use CoreGraphics mouse events carrying the Command modifier, AX geometry,
  verification and retries. SaneBar explicitly describes this as inherently
  fragile. This is the conventional automatic third-party positioning path and
  is prohibited for Blenny.
- [Thaw macOS 27 Preview 5](https://github.com/thaw-app/Thaw/releases/tag/macos-27-preview.5)
  used `TrailingItemPreferredPositions` first, nudged its own status item so
  MenuBarAgent consumed the write, verified AX order, retried key resolution and
  retained synthetic Command-drag as fallback. The release is explicitly
  experimental and outside its normal update channel. The broad macOS 27
  backport was later
  [reverted](https://github.com/thaw-app/Thaw/commit/613e7449a5b3c96fa579bbd1e838ee6424a4ff68);
  current `development` at `23dd8d3` no longer contains the runtime position
  store or global-table key and its move implementation again posts synthetic
  events. The public revert does not establish that the table itself is invalid,
  but it confirms that the complete backend is not a stable reusable contract.
- [Bartender's current macOS 27 notes](https://www.macbartender.com/goldengate/releases/)
  say item moves no longer touch the pointer. Its binary names independently show
  MenuBarAgent position read/write plans, original-position backups, a preferences
  monitor, nudge and restore paths. This strongly supports a private table-based
  implementation, while the vendor's reported drift, delayed profile applies,
  multi-item limitations, flicker and occasional unresponsive menu bar show why
  a production implementation needs repair and reconciliation behavior excluded
  from Blenny.

Therefore synthetic Command-drag is **not the only technically possible method**
on macOS 27. It remains the only broadly visible automatic technique with a
complete open-source implementation. The cursor-free alternative is the same
unsupported MenuBarAgent position-table family already tested here, and the
available products make it reliable by accepting identity heuristics, live
monitoring, retries, nudges, profile replay, fallback input synthesis or manual
repair. Those mechanisms cannot be imported into Blenny's bounded writer.

Two design ideas remain usable without copying implementation code: stable
autosave identities for Blenny-owned controls, and permutation of an already
complete position table rather than guessed absolute weights. The first can only
help the fish preserve an owner-established position. The second is blocked on
this machine because the known table is absent while a real live order exists;
creating a table from AX geometry would replace an unknown system baseline and
would not supply an exact inverse. Divider-based hiding also does not satisfy the
requested native-arrow-relative order and would regress the accepted 0.6.0
integration.

### Current decision and next implementation gate

**Real ordering exists and the self-only run proves physical control of one
third-party status-item identity on the tested runtime.** The agent position table
is a materially stronger path than changing an application's own position default.
No safe general third-party writer, bundle-wide transaction or fixed
arrow-relative layout is established.

Before any proposed write: obtain an exact legitimate readable baseline,
unambiguous owner/item mapping, documented weight/refresh semantics and an inverse
that restores actual order as well as stored keys, including absent keys and
system-item invariants. Identity must never be guessed from translated AX titles,
frames, dictionary order or a nearby icon. Do not create a guessed global table,
clear all positions, restart the agent, change Apple's item entries, or nudge a
live status item's length while physical restoration remains unresolved.

Only then can an independent Debug implementation prepare deterministic
serialization/failure/rollback tests and an installed no-write receipt with exact
targets and hashes for separate owner approval. No candidate currently qualifies
for that real-write receipt. The existing single visibility writer, accepted
0.6.0 arrow linkage, fish/arrow art and Visible / Revealable / Hidden semantics
remain unchanged. Ordinary reveal continues to exclude Hidden; Apple stays
read-only. There is no Release promotion, new release closure or tag replacement.

Raw downloads, metadata, reader failures, server diagnostics and scoped state
checks remain only under ignored `LocalData/0.7.0-api-research/`. The executable
reader and expanded metadata probe compile with Xcode 27; they are excluded from
all product/package targets. The installed app is not replaced or launched by
this follow-up.

### Ordinary and sandbox preferences differ

A fresh comparison uncovered a storage-scope ambiguity that is independently
testable without visual attendance. For the exact same Usage4Claude position
key, the standalone CFPreferences effective lookup and current-user/any-host
lookup return one numeric value, while `defaults read` and `defaults export`

ByHost override did not explain this sample.

Direct read-only file comparison establishes the two sources: the ordinary
user preference file contains the CFPreferences value, while the application's
sandbox-container preference file contains the value returned by `defaults`.
The running reference app's signed entitlements confirm App Sandbox is enabled.
Exact values, paths, hashes and entitlement output remain only in ignored
`LocalData/0.7.0-nonvisual/`; no preference was synchronized or rewritten.

The prior CFPreferences fingerprints and defaults exports compared different
storage views. Each view was internally unchanged in the retained pre/post
records; equality of either view alone does not identify what a running sandboxed
app or MenuBarAgent consumed. Consequently, the historical ineffective
third-party preference experiment cannot be generalized without establishing
its actual storage source. This is a new plausible explanation to investigate,
not proof of that historical run's cause, successful cross-app control, or a

### Application-launch scope correction

bundle identifier was absent from the frozen allowed set immediately revoked the
writer. That included ordinary applications and helper processes with no menu-bar

effective menu-bar scope had not changed.

and MenuBarAgent changes still invalidate immediately. Other new processes are
coalesced for one second and inspected together through the existing privacy-bounded,
read-only AX inventory. A complete observation proving no attributable menu-bar
item leaves the current verified assertion untouched. Any attributable menu-bar
item, failed/missing discovery, lost Accessibility, truncation or timeout fails
closed through the existing lifecycle restoration path.

This is neither polling nor reconciliation. The assessment runs once per launch
burst, does not edit policy or admit a bundle to either allow-list, and never
recreates a writer. A menu-bar owner still requires explicit Refresh/Review and

This is user-triggered bounded fallback, not polling or reconciliation. It does
not change the fish autosave identity, status-item order, policy, allow-list or
writer, and it never touches an Apple or third-party item. A width-sensitive
layout may retain the full fallback until the next explicit Reveal. Event-driven
confirmation may also expose a brief empty transition between MenuBarAgent
rendering the system control and AX delivering the corresponding layout update.
Blenny deliberately does not preemptively remove the only reveal control before
native ownership is confirmed.

recreation and length only; later installed dry-runs left the owner plist
